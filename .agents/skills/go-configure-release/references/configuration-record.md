# 发布配置记录

此记录只保存向导完成事实。生产配置值的唯一来源仍是服务成员的 `configs/config-prod.yaml` 与基线；不复制配置到记录，不依赖上一段聊天是否还在上下文中。

## 位置与字段

在真实 Workspace 根保存 `.harness/server-release/<member-directory>.json`。使用登记的成员目录作为文件名，不从产品名称或自由输入拼路径；每个成员独立记录，环境固定为 `prod`。普通 JSON 对象的合同如下。

| 字段                            | 类型与含义                                                                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion`                 | 整数 `1`；未知版本阻断，不能自动重置                                                                                                                          |
| `workspaceId`                   | 根 `.harness/workspace.json` 的实际 `id`                                                                                                                      |
| `memberDirectory`               | 精确登记的 Server 目录                                                                                                                                        |
| `environment`                   | 字符串 `prod`                                                                                                                                                 |
| `status`                        | `in_progress` 或 `configured`                                                                                                                                 |
| `sources`                       | 三项输入快照，各为 `{path, sha256}`：成员的基线 YAML、生产 YAML 与 `cmd/release-config/main.go`；路径相对 Workspace 根，SHA-256 取实际文件字节                |
| `sections`                      | 按首次引导顺序的段数组，每项含 `name`、`fields`、`status`；`fields` 为实际叶子字段路径与类型的 `{path, type}` 数组，不含值；段状态为 `pending` 或 `confirmed` |
| `sections[].confirmedAt`        | 仅 confirmed 段填写实际确认时间，带时区的 ISO 8601 字符串                                                                                                     |
| `sections[].confirmationSource` | 仅 confirmed 段填写不含答案原文的来源，如当前用户请求/会话标识；不能存含密钥的用户原话                                                                        |
| `sections[].secretBindings`     | 可选数组，每项 `{field, method, reference}`；`method` 为 `environment` 或 `file`；reference 只为实际变量名或成员相对配置路径，不含秘密值                      |
| `updatedAt`                     | 最近一次真实配置/进度写入时间，带时区的 ISO 8601 字符串                                                                                                       |

字段路径保留真实嵌套结构；列表项结构用 `[]` 描述，不保存列表内容。`type` 采用当前解析出的 `string`、`number`、`boolean`、`null`、`array` 或 `object`，复杂节点按实际结构展开。不保存逐个秘密值的哈希；输入文件整体 SHA-256 只用于变化检测，不作为配置副本或秘密验证。

## 写入与恢复

1. 在提问前解析实际配置、生成段清单。首次没有记录时只创建 `in_progress`，全部段初始为 pending；当前请求已经明确给出的答案可以直接用于对应段。只读查看配置不创建记录。
2. 每段完成后，先落生产 YAML，再重新导出和检查，最后写入该段 `confirmed` 与来源。更新三份输入快照和实际字段结构。未答段保持 pending；仅用户实际填写或明确接受现值的段可确认，局部填写依入口的其余现值核对条件处理。不能先把记录写成 configured 再补文件。
3. 等待回答或编辑期间如文件、记录被其他操作修改，停止覆盖并保留现场。单文件写入使用同目录独占临时文件和原子替换，替换前复核旧字节；失败只回收本次临时文件。配置写入成功但记录失败时如实报告，保留配置且不宣称已记录；后续先核对该差异，不静默重问或回滚用户输入。
4. 全部实际段为 confirmed、导出与当前必要检查成功、绑定与文件快照一致时才将全局状态改为 configured。部署环境秘密可以仍不在源码，前提是实际注入方式及责任已经确认；记录不证明该秘密存在或服务已启动。
5. 下次发布先核对根/成员/环境、记录结构、三份输入 SHA-256 和实际字段结构。全匹配时直接返回“复用已确认配置”，不改文件、不刷新时间、不追问配置或秘密。不能只看存在文件或 `status=configured` 就跳过解析。
6. 未完成记录从首个 pending 段继续。用户明确变更时只将请求涉及的段置为 pending，已确认的其他段及其来源保留；若变化影响相邻段，说明实际依赖并将必要联动纳入本次向导，不重问无关段。改完一段后新的全局 sources 快照只能在其他已确认段内容未变化的核对后推进；不能用全局新哈希掩盖其他段的漂移。
7. 发现输入变化时先比较实际配置和消费者。文件哈希与字段结构不能还原旧值；只有当前会话保存的输入或可信 Git 旧内容能证明不影响生效值/字段/约束的格式变化时，才可据实刷新快照，不提问。没有可信旧内容时只报告变化文件与可观察结构，不能编造旧值、新值差异或自动刷新。出现未确认的新配置、值或约束变化，或无法排除这类变化时，阻断受影响发布；未收到用户配置变更指令前不自动重开向导。新部署环境不可冒用 prod 记录，也不默认为首次全部重填。

这类用户配置记录属于本地产品事实，Harness 升级不得覆盖、删除或用源默认记录替换。源中不分发预填记录。现有 YAML 可用但没有向导记录时，首次仍需逐段让用户接受现值或修改，不从“文件存在”补造填写历史。
